a) The TinyStories tokenizer has a compression ratio of about 4.12 bytes per token, and the OWT tokenizer has a somewhat higher compression ratio of 4.37 bytes per token because it uses a larger vocabulary size. These averages were calculated by dividing the total number of bytes in the training corpus by the number of tokens generated instead of a 10-document sample.
b) The compression ratio worsened to 3.18 bytes per token because the vocabulary size declined from 32,000 to 10,000 and the two corpora have different text distributions, so the TinyStories tokenizer is not optimized for the most frequent byte pairs in the OWT corpus. When isolating for effect sizes, the compression ratio drops 0.51 when the vocabulary size declines from 32,000 to 10,000, and then another 0.69 when switching to a TinyStories tokenizer keeping vocabulary size constant, so switching the training corpus has a larger effect size.
c) The tokenizer seems to process around 12.05 MB / second for the OWT training set using six processes (total owt_train bytes over total time). At this rate, it should take 19.03 hours to tokenize the Pile dataset, since the OWT corpus is most comparable to Pile.
d) The largest token id that can appear in the encoded sequence is 31,999 since that’s the largest vocabulary size. To minimize disk space and I/O, uint16 is an appropriate choice because it’s the smallest integer width that can store the largest possible token id since the max uint16 is 65,535 and token ids are never negative.
